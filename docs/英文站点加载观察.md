# 英文站点加载观察

**目的**：拿一批**真实的、国内访问量靠前**的英文站点，实测「英文网页阅读器」抓取与排版的实际效果，找出真问题。

**站点清单**：`docs/英文站点样本.txt`（72 个 URL，分 10 类）
**探测方式**：逐个送进 `/api/article`，全部实测，不靠推测（脚本 `server/scripts/probe-sites.mjs`）
**样本日期**：2026-10-05
**机器位置**：南京，家用宽带（这一点很重要，见 §3.1）

---

## 1. 三句话结论

1. **阅读器本身表现是好的**——72 个站点里 40 个失败，但其中 **22 个连 curl 都拿不到**（网络层不通）、**12 个是站点明确反爬（403 等）**。真正属于我们自己的问题只有 **1 个**，且已修。
2. **效果好坏由「页面类型」决定，不由「站点」决定**。标准文章页 / 文档页效果很好（正文干净、层级正确、列表保留）；**首页 / 栏目页会很差**——它们不是文章，抽出来的是碎片，而且**看起来还挺像一篇文章**，用户不会觉得是出错了。
3. **部署位置决定了能抓什么**。本机在南京，国际新闻大站（BBC / Reuters / NYT / Guardian…）全军覆没；换到境外环境，这批会反过来能抓。这是发布前必须确认的事。

## 2. 总览

| 指标 | 数值 |
|---|---|
| 站点总数 | 72 |
| 抓取成功 | **32（44%）** |
| 其中提取质量好（≥10 块且正文 ≥1500 字） | **11** |

## 3. 失败归因：哪些是我们的锅，哪些不是

40 个失败逐个用 `curl` 直连复核（绕过阅读器），分成三类：

| 归因 | 数量 | 说明 |
|---|---:|---|
| **网络层不通** | **22** | curl 也拿不到（`000`，超时或被重置）。属于本机网络环境限制，**与阅读器无关** |
| **站点明确拒绝** | **12** | 返回 403 / 401 / 402 / 202，是反爬或需登录。属预期，诚实报错即可 |
| **需要具体分析** | **6** | 直连能拿到、但我们失败或归属不准 —— 逐个查证，见 §3.3 |

### 3.1 网络层不通的 22 个（直连同样失败）

`bbc.com` `reuters.com` `nytimes.com` `theguardian.com` `wsj.com` `economist.com` `ft.com` `bloomberg.com` `businessinsider.com` `forbes.com` `latimes.com` `abc.net.au` `aljazeera.com` `en.wikipedia.org` `news.ycombinator.com` `reddit.com` `medium.com` `quora.com` `ai.meta.com` `huggingface.co` `pubmed.ncbi.nlm.nih.gov` `github.com`

> **这组数字的含义**：不是"阅读器抓不到新闻站"，而是"**这台机器连不上这些站**"。
> 阅读器是**服务端抓取**，所以它能不能用，取决于**部署在哪**。
> 发布到境外沙箱后这一批大概率会反过来变成可抓 —— 需要在发布后重跑一次这份清单来确认。

**顺带一个观察**：同一站点两次探测可能给出不同结果（`github.com`、`npmjs.com`、`nodejs.org` 都出现过翻转）。说明网络层本身不稳定，**错误码只能提示"性质"，不能当精确定位用**。

### 3.2 站点拒绝的 12 个

`apnews.com` `arstechnica.com` `news.sky.com` `openai.com` `stackoverflow.com` `bleepingcomputer.com` `britannica.com` `ebay.com` `npmjs.com` `marketwatch.com` `usatoday.com` `engadget.com`

返回 403 / 401 / 402 / 202。这是**诚实报错**的场景——PRD 定的策略就是不绕过反爬。

### 3.3 需要具体分析的 6 个

| 站点 | 直连 | 我们的结果 | 查证结论 |
|---|---|---|---|
| `docs.nestjs.com` | 200 | `extract_failed` | **是真问题，已修**，见 §5.1 |
| `edition.cnn.com` | 200 | `blocked_by_site` | 同一 URL 同一 UA，curl 拿 200、我们拿拒绝。怀疑 CDN 按请求头组合识别人机（我们发了 `Accept-Encoding: identity`，比较少见）。**未修**，记为待查 |
| `www.amazon.com` | 200 | `extract_failed` | 首页本身没有文章正文（导航 + 商品位），**报"没认出正文"是诚实的** |
| `www.nature.com/...` | 303 | `blocked_by_site` | 303 跳转后的落点拒绝，属站点行为 |
| `nodejs.org/en/learn/...` | 307 | `timeout` | 307 跳转后超时，且两次探测结果不一致，判定为**网络抖动** |
| `www.tomshardware.com` | 200 极慢 | `timeout` | 直连 8s+ 都没返回完，**是真慢**，报超时正确 |

**结论：40 个失败里，真正属于我们的只有 1 个。**

## 4. 效果分级：问题不在站点，在页面类型

把 32 个成功的按**效果**排一下，规律非常清楚。

### 好 —— 标准文章页 / 文档页

| 站点 | 块数 | 正文字数 | 观察 |
|---|---:|---:|---|
| `docs.aws.amazon.com` | 117 | 33755 | 标题、正文、列表层级全对，无导航污染 |
| `scientificamerican.com` | 76 | 5087 | 抓到的第一段就是文章导语 |
| `react.dev` | 66 | 11724 | 24 个代码块全部跨栏显示 |
| `un.org` | 75 | 13179 | 段落完整 |
| `developer.mozilla.org` | 48 | 9636 | 基准用例 |
| `anthropic.com` | 34 | 12701 | 4 张插图完整跨栏 |

**这类页面可以放心用**：结构正确、代码块与图片跨栏、左右对齐稳定。

### 差 —— 首页 / 栏目页（21 个"提取偏少"几乎全在这里）

| 站点 | 块数 | 阅读器里实际看到的 |
|---|---:|---|
| `npr.org` | **1** | 标题 + **一段网站自我介绍**（meta description），新闻列表全没了 |
| `techcrunch.com` | 4 | 只抽到**其中一张卡片** |
| `theverge.com` | 3 | 同上 |
| `cnbc.com` | 2 | 一条标题 + 一句摘要 |
| `nasa.gov` / `who.int` / `gov.uk` | 4 / 20 / 11 | 抓到的是导航与栏目名 |
| `arxiv.org` | 4 | 抓到的是页面按钮（"View PDF HTML"），不是摘要 |

> **这是本轮最重要的发现。**
> 这些结果**看起来像一篇很短的文章**，而不是"出错了"——用户不会发现粘错了链接。
> 现有的 `extract_failed` / `js_rendered` 只能表达"抓不到"，表达不了"抓到了，但这不是一篇文章"。
> 这是当前最值得补的一个产品缺口（见 §6）。

### 中 —— 能读，但有杂质

| 站点 | 块数 | 问题 |
|---|---:|---|
| `learn.microsoft.com` | 36 | 降级到启发式提取（`heuristic`） |
| `blog.google` | 29 | 同上 |
| `technologyreview.com` | 132 | 抓多了，把栏目导航也带了进来 |

## 5. 本轮发现并已修的两个问题

两个都是**实测数据带出来的**，不是读代码看出来的。

### 5.1 `docs.nestjs.com`：SPA 判定漏了 Angular

**现象**：直连 200、HTML 有 19.8KB，我们报 `extract_failed`（"没能识别出正文"）。

**查证**：用 `diag-extract.mjs` 分层定位 + 直接扒 DOM，发现该页是 Angular 外壳（`<app-root>`），页面上**几乎没有可见文字**；那 19.8KB 里所谓"正文"其实是 `<script>` 里的数据载荷。

**两个具体缺陷**：

1. **SPA 挂载点清单不全**：只认 `#app / #root / #__next / [data-reactroot]`，漏了 Angular 的 `<app-root>` 与 `[ng-version]`、Nuxt 的 `#__nuxt`。
2. **文本长度口径错了（更要命）**：判定用的是 `body.textContent`，它**把 `<script>` / `<style>` 里的代码也算作文本**。实测该页可见文字接近 0，却因为有 1851 字的 service-worker 代码被判成"有内容"，于是绕过了 SPA 判定，最后只能报笼统的 `extract_failed`。

**修法**（`extract.service.ts`）：

- 新增 `visibleTextLength()`：克隆 body、剔除 `script/style/noscript/template` 后再数长度；
- `looksLikeSpa()` 的挂载点选择器补上 `app-root`、`[ng-version]`、`#__nuxt`。

**效果**：`docs.nestjs.com` 现在正确报 `js_rendered` → 用户看到"**页面内容靠脚本渲染，抓不到正文**"，而不是含糊的"没能识别出正文"。

### 5.2 「被重置」被错报成「超时」

**现象**：`huggingface.co` 只用了 **73 毫秒**就失败，错误提示却是"**抓取超时，网站响应太慢**"。

**根因**：`mapNetworkError()` 把 `ECONNRESET` / `EPIPE` 一并映射成了 `timeout`。

**为什么这不能忍**：两者能拿到同样的失败结果，**性质却完全相反**——一个是"对方立刻把连接掐了"（73ms），一个是"对方太慢"（25s）。提示写"网站响应太慢，稍后再试"会把用户引向完全错误的动作（在那儿干等）。这正是技术方案 §4.4 记下的那条教训的同类问题：**失败结果相同不代表失败原因相同**。

**修法**：

- 新增错误码 `connection_reset`（502，"连接被中途断开，没能取到内容 · 常见于网络环境对该站点的限制，或对方服务器主动断开"）；
- `ECONNRESET` / `EPIPE` / `ENETUNREACH` / `EHOSTUNREACH` 归到它；`ETIMEDOUT` / `ESOCKETTIMEDOUT` 保留 `timeout`；
- 前端 `types.ts` 的错误码联合类型同步。

**效果**：`huggingface.co`、`reddit.com` → `connection_reset`；`bbc.com` → `timeout`（真·10 秒无响应）。两者现在能分开了。

## 6. 对产品的含义（建议）

按优先级：

1. **补"这不是文章页"的识别**（最重要）。现在首页会被渲染成一篇很短的假文章，用户看不出来。做法可以先粗后细：正文块数极少 + 页面本身有大量链接 → 在文章头给一条提示（"这看起来不是一篇文章，你可能粘到了首页"），而不是静默出一个残缺结果。
2. **发布后重跑这份清单**。本机在南京，22 个"网络不通"是环境结论，不是产品结论。部署到境外沙箱后必须重测，否则会把环境限制误当成产品能力边界。
3. **查 `edition.cnn.com` 的请求头问题**。同一个 URL 同一 UA，curl 200 我们被拒，怀疑是请求头组合（尤其 `Accept-Encoding: identity`）触发了 CDN 人机识别。若属实，换掉这一个头就能多救一批站。
4. **给慢站加进度反馈**。目前最慢的成功请求 19.4s，接近 25s 上限；用户这 20 秒里只看到骨架。

**不用管的**：12 个反爬站点。首版策略是诚实报错、不绕过，这个取舍是对的。
